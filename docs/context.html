Domain Context: Spec Compiler

Ein Kontext, zwei normalisierte Modelle und drei explizite Produktprotokolle.

Decision and Obligation Compilation bleibt eine Fähigkeit desselben Spec Compiler. KfW und Cloud Compliance nutzen gemeinsame Decision-Semantik, aber getrennte Domain Ontologies. Evidence Requirements und Rule-imposed Obligations werden unabhängig ausgewertet.

The repository contains one bounded context: the Spec Compiler. It turns explicit product specifications into deterministic contracts, proofs, and work guidance while keeping generated products behind observable, technology-neutral boundaries.

Current models

The compiler normalizes the SQL/OpenAPI profile into an Explicit Obligation Model and the first decision profile into a typed, immutable Explicit Decision and Obligation Model. All generated requirements come from an explicit spec statement or a named, versioned convention. Ambiguous or unsupported input is rejected, and generated product tests remain black-box tests.

Implemented decision slice

ADR 0016 accepts a bounded path toward Decision and Obligation Compilation. ADR 0017 implements its first profile with source-backed Rules, Conditions, Fact Gaps, Decision Results, and Provenance without weakening the existing provenance invariant. ADR 0018 adds explicit Fact Questions and deterministic Next Question selection from current Fact Gaps. ADR 0019 adds independently sourced Evidence Requirements, explicit Evidence Assessments, and Evidence Requirement Evaluations without changing Condition truth or Decision Outcomes. ADR 0020 adds Version Selection Conventions v1: a stable Rule Set and explicit Decision Date select exactly one source-backed Rule Set Version without a today/latest default. ADR 0021 implements Rule-imposed Obligations and independent evaluation in the Cloud Privileged-Access Compliance Slice. ADR 0022–0024 add an optional authored HTTP contract to the KfW reference product.

The first implementation slice is the KfW 458 Applicant Eligibility Pilot. It is invoked through Decision Protocol v1 and compiles two historical Rule Set Versions into a Decision Contract, generated proofs, and observable eligible, ineligible, or unknown Decision Results. An unknown result carries one source-justified Next Question; repeated complete Case submissions advance to another justified question or a determinate outcome. Its scope and source revisions are defined in the Decision and Obligation Compilation roadmap. For self-using owners claiming the modeled bonuses, the same Decision Result also reports the independent ownership Evidence Requirement as fulfilled, missing, or not_applicable and classifies supplied Evidence.

Domain language

The canonical terms, relationships, and aliases to avoid are maintained in docs/glossary.html. Architecture documents, ADRs, ontology terms, code, and generated work items use that language.

Invariants

  • External source documents do not directly become generated requirements; an authored Spec cites a Source Citation, and generated output remains traceable to that Spec or to a named, versioned convention.
  • A missing decision fact yields an explicit Fact Gap and may yield an Undetermined Decision Outcome. It is not inferred as false.
  • A Next Question is selected only from current Fact Gaps while the Decision Outcome is undetermined. Its authored priority is explicit and determinate outcomes never request another Fact.
  • A satisfied Condition does not fulfill an Evidence Requirement. Only matching Evidence with an explicit accepted Evidence Assessment can do so under Evidence Evaluation Conventions v1; the requirement keeps its own Source Citation.
  • Ambiguous specs, conflicting facts, ambiguous rule-set applicability, or multiple incompatible conclusions are errors, not Undetermined outcomes.
  • A Decision Request supplies a stable Rule Set and Decision Date. The Rule Set Version is derived only from authored half-open Validity Periods and is reported in every result; it is never selected by the caller or wall clock.
  • The Spec Compiler remains one software system. Decision and Obligation Compilation is a capability of it, not a second system.
  • Reusable decision semantics and domain vocabulary remain separate. A funding term does not enter the Decision and Obligation Core Ontology merely because it appears reusable.
