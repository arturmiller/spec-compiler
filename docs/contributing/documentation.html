Mitwirken · unterstützende Infrastruktur

Die Website entwickeln und veröffentlichen.

Diese Pipeline dokumentiert den Compiler. Sie erzeugt keine Produktverpflichtungen und gehört nicht zum fachlichen Kompilierungspfad.

Änderungen vor dem Deployment ansehen

uv run --extra dev poe documentation-preview

http://127.0.0.1:8080/ zeigt denselben Build wie GitHub Pages. Gespeicherte HTML-, JSON- und RDF-Quellen werden neu gebaut; fehlerhafte Kandidaten ersetzen den letzten gültigen Stand nicht. Nur der lokale Server ergänzt Reload und Fehleranzeige.

uv run --extra dev poe documentation-site
uv run --extra dev python tools/preview_documentation.py --port 8081 --base-path /spec-compiler/

Auch --quick erneuert Referenzen und RDF-Exporte. Ein gespeicherter Quelltext führt nicht zu einem Push oder Deployment.

Eine Quelle pro Information

Redaktionelles HTML enthält Texte. JSON-Modelle beschreiben Diagramme samt Kurzbeschreibung, Langtext und geprüften Glossarlinks. Turtle definiert die Ontologien. Pflegeregeln verhindern parallele Markdown-/Mermaid-Wahrheiten; generierte Work Items bleiben Markdown.

Die unterstützende Build-Architektur

Documentation Site Builder komponiert HTML, Navigation, Suche und Archify-Artefakte. Ontology Documentation Builder verwendet RDFLib für zweisprachige Referenzen und semantisch unveränderte Exporte sowie Graphviz/Cytoscape für feste Graphansichten. Documentation Preview Server ergänzt nur lokal Watch und Reload.

Diese Werkzeuge bleiben Teile der Repository-Toolchain. Eine getrennte Dokumentationsansicht behauptet weder eine neue Produktgrenze noch ein neues Laufzeitprotokoll. Node, Graphviz und die lokale Archify-Kopie sind Build-Abhängigkeiten, keine Produktanforderungen. Java/WIDOCO werden nicht benötigt.

Der zentrale Ontologiegraph zeigt sieben wiederverwendbare Module und über einen Toggle zusätzlich abschließende Produktspezifikationen. Er entsteht aus lokalen Ontologie- und Produkt-RDF-Dateien. Explizite Imports sind Kanten; Begriffsverwendung prüft, ob Imports fehlen. docs/diagrams/ontology-dependencies.json besitzt das Layout und die Knotenerklärungen für die ergänzende Architektursicht; auch deren Connections werden aus RDF abgeleitet. Alte Übersichtslinks führen zum zentralen Graphen. Zusätzliche Unterkapitel und Property-Kataloge entfallen. Keine Remote-Auflösung und keine manuell gepflegten Abhängigkeiten. Graph öffnen.

Veröffentlichen

GitHub Actions prüft den vollständigen Workflow und baut die statische Website. Pull Requests werden ohne Veröffentlichung gebaut. Ein Push auf main veröffentlicht das geprüfte Artefakt über GitHub Pages.

Beziehungen in Begriffsgraphen

Die Ansicht enthält alle lokalen Klassen und benannten Einzelwerte, auch wenn beide gemeinsam vorkommen. Rechtecke sind Klassen, Sechsecke benannte Einzelwerte; externe Nachbarbegriffe tragen einen gestrichelten Rand und nennen ihre Herkunft. rdf:type-Kanten sind als Typzuordnung von Unterklassenbeziehungen getrennt. Ein konkreter Wert wie SQLite wird nicht zur Klasse umgedeutet.

Der Toggle „Externe Begriffe einblenden“ ist zunächst aktiv. Deaktiviert zeigt er nur Knoten der ausgewählten Ontologie und blendet alle Kanten zu versteckten Knoten aus. Der Zähler und die Beziehungsliste berücksichtigen diese Sichtbarkeit. Ein ausgeblendeter ausgewählter Knoten wird durch einen lokalen ersetzt, ohne Layout, Zoom oder Pan zu ändern. Die Einstellung bleibt beim Graphwechsel erhalten und ist als external=0 in der URL teilbar. In der Importübersicht ist der Toggle verborgen; der Produktspezifikationen-Toggle bleibt davon unabhängig.

Kanten entstehen ausschließlich aus lokalen Deklarationen: Unterklassen, expliziten Typzuordnungen lokaler Einzelwerte, Objekt-Property-Domains/-Ranges und klassenlokalen owl:allValuesFrom-Beschränkungen. Benannte externe Endpunkte sind direkte Kontextknoten; auch eine lokale Property darf zwei externe Klassen verbinden. Der gemeinsame lokale Katalog liefert nur Labels, Beschreibungen und Referenzlinks, keine zusätzlichen Kanten und keine rekursive Importexpansion. Standardbegriffe haben feste Anzeigelabels; es gibt keine Remote-Auflösung. JSON-Felder erzeugen keine Graphkanten.

Zieltyp-Beschränkungen verlangen kein Vorkommen einer Beziehung und bleiben im Detailbereich markiert. Andere anonyme OWL-Ausdrücke werden nicht als einfache Kante interpretiert. Literale bleiben Properties im Detailbereich; veraltete Properties tragen einen Hinweis. Offen deklarierte Domains oder Ranges werden nicht aus Beispielen geraten. Auswahl, Suche und Beziehungsfilter verändern keine Positionen und keinen Ausschnitt. Die Ergebnisbeziehungen aus ADR 0032 und die Vervollständigungen aus ADR 0033 stammen aus RDF, nicht aus Renderer-Heuristiken.

Unterstützungsinventar pflegen

Der Compiler Support Inventory Builder liest docs/reference/compiler-support.html und die kanonischen Turtle-Dateien. Die HTML-Quelle besitzt Verwendungsmuster und Zuordnungen; RDF bleibt die einzige Quelle für Begriffsdefinitionen. Der Documentation Site Builder ergänzt den abgeleiteten Begriffsindex, die Suchziele und reference/compiler-support.json. Lokaler Einzelaufruf: uv run --extra dev poe support-inventory; der Export liegt dann unter build/compiler-support.json. Beide Standardvalidierungen prüfen dasselbe Inventar.

Ein Muster ist ein article mit identischen id und data-support-pattern. Es nennt data-profiles, data-roles, data-status, data-evidence, explizite data-terms und gegebenenfalls data-standards. Die Textfelder data-support-field="title", conditions und limits sind verpflichtend. Modulzwecke stehen an data-support-module/data-purpose; eine neue Ontologie benötigt eine ausdrückliche Einordnung.

Links mit data-support-ref sind implementation, test, convention oder followup. Python-Referenzen nennen mit data-symbol eine existierende Funktion oder Klasse, Tests eine Prüffunktion. Konventionen verweisen auf lokale HTML-Anker. Ein Status missing oder unsupported benötigt das Textfeld gap und eine konkrete Folgezuordnung. Rollen und zulässige Statuswerte sind im Validator festgelegt; der Anfangskern ist noch nicht beschlossen.

Bei Verhaltensänderungen die tatsächliche Aussage jedes Musters und seiner Tests prüfen. Automatische Referenzprüfung ist keine semantische Oracle. Neue öffentliche Begriffe, Standardzugriffe im Reader und HTTP-Schema-Keywords ohne Einordnung werden zurückgewiesen. Der JSON-Export wird abgeleitet und nicht von Hand gepflegt. Referenz öffnen · ADR 0034.

Die lokale Archify-Erweiterung pflegen

summary enthält die sichtbar umbrechende Knotenerklärung; description enthält Aufgabe, Eingaben, Ausgaben und Grenzen in der Detailansicht; links verweisen auf Glossar oder vertiefende Seiten. Lange Texte werden nicht durch kleinere Schrift versteckt. Modelle, Schemas, generierte Validatoren und Viewer müssen zusammenpassen. ADR 0029 dokumentiert den Wartungsaufwand.

Der Build prüft Quellen, Seitenlinks, Suchziele, Diagrammschemata und neun Showcase-Artefaktchecks. Browser-Containment und visuelle Review sind eigene Nachweise. Generierte Websites werden nicht eingecheckt. Alte generierte Dateien werden nur im validierten abgeleiteten Build-Verzeichnis entfernt.
