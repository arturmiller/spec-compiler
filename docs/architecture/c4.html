Spec Compiler – C4-Modell

This document applies the C4 model to the current prototype. It deliberately separates four concepts:

  1. the executable Spec Compiler,
  2. the static Product Workspace, and
  3. the separately executable Generated Product, and
  4. the compiler's static Spec Compiler Self-Description Bundle.

The diagrams describe implemented structure, including ADR 0017's first Decision and Obligation Compilation slice, ADR 0018's question flow, ADR 0019's evidence evaluation, ADR 0020's historical version selection, and ADR 0021's cloud-compliance reuse and Obligation evaluation. Later roadmap concepts remain explicitly classified without being drawn as current runtime structure.

Die verbindlichen Diagrammquellen sind docs/diagrams/*.json. Der lokal gepinnte Archify-Renderer erzeugt daraus HTML; C4-Elementtypen, Technologien, Verantwortlichkeiten und Beziehungslabellen tragen die fachliche Semantik. Die Ansichten sind in arc42 eingebettet.

Scope: the Spec Compiler and its direct users and neighboring software systems. Audience: everybody involved in specifying, implementing, or reviewing products.

The AI Coding Agent is conceptual and optional. Today the toolchain creates a file-based handoff; it does not invoke an agent API.

Compiler products are replaceable roles, not a dedicated product class. Their specs separate the general Software Application, its Compiler Protocol conformance, and the Transformation Contract it implements. Optional Bootstrap Process provenance names a seed and evolution strategy without constraining the product contract to the seed's technology.

The checked-in Decision Product CLI and Decision HTTP Adapter both use the evaluator in app.py and read generated/decision-contract.json; the HTTP adapter additionally serves generated/expected-openapi.json. They are separately started processes, not a runtime service-to-service call. Decision Protocol v1 does not require products to read that file or use Python. The external KfW Source Revisions are not fetched at runtime; their immutable identities, validity, and authored Source Citations were validated during compilation. Repeated requests are independent Decision Protocol v1 invocations or HTTP POSTs; the client retains and resubmits accumulated Case Facts, so no session Container or UI is introduced. Evidence values in the JSON exchange are semantic identities, types, and Assessments; no document upload or storage Container is introduced.

Cloud Privileged-Access Compliance product

Code level

A C4 Code diagram is intentionally omitted. The compiler and runner are small, and function-level details are already visible in source and in the Component views. A Code diagram should be added only if a stable internal model emerges whose relationships are not evident from the code.

Current and target classifications

These classifications distinguish the implemented Issues #3 through #6 slices from later roadmap work.

Target concept C4 classification Boundary consequence
Decision and Obligation Compilation Implemented capability of the existing Spec Compiler Software System It is not a second Software System and does not create a new tool boundary.
Explicit Decision and Obligation Model Implemented typed in-memory data inside the Spec Compiler CLI Container It is not a Container; version-selection, decision, question-flow, obligation, evidence-evaluation, and provenance subsets are materialized.
Decision and Obligation Core Ontology Implemented authored public vocabulary data store It is published separately from the SHACL Contract Ontology.
Funding Domain Ontology Implemented authored public vocabulary data store Funding terms remain outside the decision core and compiler protocol vocabulary.
Cloud Compliance Domain Ontology Implemented authored public vocabulary data store Cloud identity and compliance terms remain outside the decision core, funding vocabulary, and compiler protocol vocabulary.
KfW Source Revision External static source artifact referenced by authored Source Citations The initial compiler does not fetch, scrape, or interpret it at runtime.
NIST Source Revision External static source artifact referenced by authored Source Citations SP 800-53 and SP 800-53A remain separate provenance inputs and are not fetched or interpreted at runtime.
Decision Product Implemented Generated Product role behind Decision Protocol v1 JSON standard streams are contracted; UI, language, and framework are not.
HTTP Contract Conventions v1 Implemented general HTTP message and body-binding interpretation, integrated with Decision Products Product-authored request/result/error schemas and sco:invokesContract supply generated OpenAPI and HTTP proofs; no new runtime Container is implied.
Fact Question and Question Flow Case Implemented authored semantics compiled into the Decision Contract and generated proofs They add no runtime Container; clients resubmit accumulated Case Facts through stateless protocol invocations.
Evidence Requirement evaluation Implemented semantic extension of the existing capability and typed model It adds no document store or validation service; Evidence and Assessments cross the existing Decision Protocol boundary.
Version Selection Conventions v1 Implemented semantic extension of the existing capability and typed model Stable Rule Set plus explicit Decision Date selects exactly one authored version; it adds no service or runtime source fetch.
Obligation Evaluation Conventions v1 Implemented semantic extension of the existing capability and typed model Explicit Rule-imposed Obligations project the Rule Condition state and cross the existing Decision Protocol boundary; lifecycle and remediation remain out of scope.

The detailed target semantics and pilot scope are in the Decision and Obligation Compilation roadmap and ADR 0016 plus ADR 0017, ADR 0018, ADR 0019, and ADR 0020, plus ADR 0021 and ADR 0022, as refined by ADR 0023 and ADR 0024.

Model maintenance

The rules in Dokumentationsstandard are normative. In particular:

  • preserve the system boundary between Spec Compiler and Generated Product;
  • keep the canonical names used in this document;
  • update relationships and technologies in the same change as code;
  • do not present the optional AI Coding Agent as an automated integration until such orchestration exists;
  • do not add conceptual product layers that are absent from the implementation.
  • keep later Decision and Obligation Compilation concepts out of implemented diagrams until their vertical slices change the actual structure.
