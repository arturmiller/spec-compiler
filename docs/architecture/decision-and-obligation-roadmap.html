Decision and Obligation Compilation roadmap

Status: Living roadmap. The architectural basis was accepted in Issue #1; the first runtime slice is implemented by Issue #2 and ADR 0017. Issues #3 through #5 implement question selection, evidence evaluation, and historical Rule Set Version selection. Issue #6 and ADR 0021 add the first cross-domain reuse proof and activate explicit Rule-imposed Obligations.

Purpose

The Spec Compiler will evolve from compiling externally testable product obligations toward Decision and Obligation Compilation for arbitrary software-development domains. The evolution preserves the existing principles: explicit provenance, deterministic generation, black-box product verification, and failure on ambiguity.

This roadmap fixes vocabulary, semantic boundaries, ontology ownership, a first pilot, and non-goals. It distinguishes the implemented decision, question-selection, evidence-evaluation, version-selection, and narrow obligation-evaluation slices from later Obligation lifecycle work.

Semantic model

The typed, immutable Explicit Decision and Obligation Model now exists alongside the SQL-oriented Explicit Obligation Model. Issue #2 materializes the decision, rule, condition, case, fact-gap, and provenance subset. Issue #4 adds the evidence-requirement subset and Issue #5 adds source-backed historical Rule Set Version selection. Issue #6 activates explicitly authored, Rule-imposed Obligations through Obligation Evaluation Conventions v1.

Concern Accepted semantics
Facts Only explicitly supplied Facts are available; absence never implies false.
Conditions Each Condition evaluates to satisfied, violated, or unknown. An unknown evaluation identifies its Fact Gaps.
Rules Each Rule explicitly identifies its Conditions and conclusion or Obligation; the compiler does not invent an aggregation rule.
Decisions One Decision evaluates one scoped question for one Case against exactly one Rule Set Version.
Outcomes A uniquely entailed domain outcome is returned. The serialized outcome unknown is returned only when Fact Gaps prevent a unique outcome.
Errors Ambiguous specs, conflicting Facts, ambiguous Rule Set Version applicability, unsupported constructs, and multiple incompatible entailed outcomes fail with diagnostics rather than becoming unknown.
Obligations An Obligation exists in a result only when an explicitly sourced Rule imposes it. Its Condition maps satisfied to fulfilled, violated to violated, and unknown to unknown.
Evidence Evidence Requirements and supplied Evidence are distinct from the Fact or Obligation they support; presence of Evidence is not automatically conclusive.
Provenance Results link through Rules and authored Spec statements to Source Citations, or directly to a named, versioned convention where that convention is the permitted requirement origin.
Time Validity Periods are half-open (validFrom inclusive, validUntil exclusive). A Decision Date has no implicit today/latest default.

A complete Case with no uniquely entailed outcome indicates an incomplete or ambiguous decision specification and is an error. An incomplete Case may produce unknown only when the identified Fact Gaps are sufficient to explain why a unique outcome cannot yet be derived.

The sdo:, funding:, and cloud: namespaces are published as separate authored vocabularies with their own WIDOCO references and WebVOWL graphs. The Decision and Obligation Core Ontology does not import the SHACL Contract Ontology merely because both are compiled by the same system. Evidence terms are present because Issue #4 establishes executable semantics; Obligation terms are present because Issue #6 establishes their narrow executable semantics.

A domain concept may be promoted to the core only after at least two distinct domains use it with the same semantics and the promotion is recorded as an architectural decision. Issue #6 supplies the first cross-domain test without promoting a domain term.

KfW 458 Applicant Eligibility Pilot

Decision question

For a natural-person Case, determine whether the supplied applicant facts satisfy the modeled applicant-eligibility rules of KfW product 458 under the Rule Set Version selected by the explicit Decision Date.

eligible means only a positive answer to this scoped applicant question. It is not a statement about measure eligibility, application completeness, funding amount, KfW approval, available budget, or legal entitlement.

Source selection review

The official KfW document catalogue identifies a July 2026 revision and retains the December 2025 revision separately. Both PDFs state their validity dates. Page 2 of the December revision lists the GbR exclusion but no usufruct exclusion; page 2 of the July revision adds that exclusion. Therefore identical modeled usufruct-applicant Facts yield eligible on 2026-07-20 and ineligible on 2026-07-21. The July PDF declares Stand 07/2026, Bestellnummer 600 000 5131, and validity from 2026-07-21. Its page 2 contains the selected applicant categories and explicit exclusions. Page 8 separately requires self-using owners claiming the climate-speed or income bonus to submit a land-register excerpt as ownership Evidence. The recorded lengths and SHA-256 values identify the exact current bytes reverified on 2026-09-08 and the archived bytes reviewed on 2026-09-08.

The Merkblatt states that the program is based on the BEG EM guideline, but the pilot deliberately compiles only the product-specific applicant passage. If a later Rule depends on BEG EM, technical requirements, FAQs, or another KfW document, that document must be registered as its own pinned Source Revision and cited explicitly; authority is never inherited through an unmodeled link.

The version catalogue is evidence for document identity and version history; it does not itself supply compiled eligibility Rules. Both selected Merkblatt revisions are external Source Revisions. An authored Spec must represent and cite each selected statement before it can produce a generated requirement or result.

Pilot boundary

The first slice supports only the natural-person category and the applicant facts needed to distinguish ownership from the explicitly excluded GbR and usufruct cases for an existing residential building in Germany. A negative naturalPerson Fact means only that this scoped category is not satisfied; other applicant categories, including a Wohnungseigentümergemeinschaft, require their own Decision Contract and are not assessed as program-wide ineligible.

The pilot produces:

  • eligible when a unique positive applicant-eligibility conclusion is entailed;
  • ineligible when a source-backed applicant exclusion or failed necessary applicant condition entails that conclusion;
  • unknown when one or more named Fact Gaps prevent a unique conclusion;
  • one source-justified Next Question, selected deterministically from the current Fact Gaps while the outcome remains unknown;
  • an independent ownership Evidence Requirement Evaluation of fulfilled, missing, or not_applicable, with classifications for supplied Evidence and its own page-8 Source Citation;
  • an error for input outside the pilot boundary, conflicting Facts, ambiguous Rules, or a missing or non-unique applicable Rule Set Version.

Version Selection Conventions v1 use only the stable Rule Set, the explicit Decision Date, and the authored half-open Validity Periods. The caller cannot pin a version and no today/latest default exists.

Explicitly excluded from the pilot

  • technical eligibility of a heating system or measure;
  • subsidy rates, bonuses, eligible costs, calculations, and combinations;
  • application timing, contracts, forms, document upload/storage, automated document-content or authenticity validation, or approval;
  • automatic ingestion, interpretation, or monitoring of KfW documents;
  • coverage of other KfW, BAFA, state, federal, or EU programs;
  • legal, financial, or funding advice and any promise of approval;
  • a conversational user interface or production deployment.

Decision question and sources

The authored citations point to IA-2 and IA-2(1) on PDF page 158 (printed page 132) and to the IA-02(01) assessment objective and methods on PDF pages 255–256 (printed pages 244–245). The compiler does not fetch or interpret these documents. It verifies the explicit revision identities and compiles the authored statements.

The complete positive Question Flow Case starts without Rule Facts, asks only the currently decision-relevant questions, and reaches satisfied after the authored answers are submitted. Separate Cases prove violated and unknown, all three Evidence Requirement statuses, and all three Obligation statuses. The MFA Evidence Requirement remains independent: missing assessment evidence does not turn a satisfied policy Condition into a violation.

After these original slices, ADR 0022 adds an authored Decision POST endpoint and generated OpenAPI to the KfW reference bundle. It exposes the same applicant-eligibility Decision Contract; no UI or funding-amount calculation is added. ADR 0023 types that endpoint as generic sco:PostEndpoint and selects its Decision semantics through the explicit versioned mapping. ADR 0024 then replaces that mapping with concrete product-authored HTTP messages, JSON Schemas, response statuses, media types, and body-pointer bindings.

Each slice must update architecture and ontology documentation with its actual implementation, regenerate outputs twice with byte-identical results, and pass the complete workflow.

Cross-slice guardrails

  • The Spec Compiler remains the software system; Decision and Obligation Compilation is a capability selected by explicit contract/protocol semantics.
  • A source parser, scraper, crawler, or LLM is not part of deterministic compilation. Source-to-Spec curation is a separate authored step.
  • New output formats or runtime interactions require explicit, versioned contracts before generated assertions can rely on them.
  • Generated tests observe products through declared black-box boundaries and do not import their implementation modules.
  • No UI, framework, programming language, file format, or deployment topology is inferred from the funding pilot.
  • Deterministic output never substitutes for semantic correctness; independent examples and review remain necessary.
