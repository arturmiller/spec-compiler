Lebende Architektur · aktueller Prototyp

Alle zwölf arc42-Abschnitte bleiben erhalten. C4-Ansichten sind hier eingebettet; Modell und Klassifikation enthalten die ergänzende Referenz. Verbindliche Regeln stehen in den Generierungsprinzipien.

1. Einführung und Ziele

Der Spec Compiler übersetzt explizite RDF/SHACL-Specs deterministisch in Verträge, Black-Box-Nachweise und begrenzte Work Items. Er erfindet keine Anforderungen und legt keine Produkttechnologie fest. Aktuell existieren SQL/OpenAPI-, Decision- und Compilerprofile sowie eine optionale, ausdrücklich spezifizierte HTTP-Schnittstelle.

Die wichtigsten Qualitätsziele sind Anforderungsintegrität, Reproduzierbarkeit, Produktunabhängigkeit, Rückverfolgbarkeit und sicheres Prozess-Cleanup. Das Projekt ist ein Prototyp, kein vollständiger SHACL-Compiler oder Produktionsdeployment.

Vollständige technische Details (bestehende englische Fassung)

1.1 Requirements overview

The Spec Compiler explores whether RDF/SHACL product specifications can be compiled deterministically into executable contracts, tests, and small work items that guide stochastic product-code generation.

The toolchain must:

  • read explicit domain, HTTP, storage, decision, rule, and provenance statements from Turtle specs;
  • reject missing, ambiguous, or unsupported information instead of guessing;
  • derive profile-specific compiled contracts, black-box tests, a Work Graph, and issue text from one normalized model per compiler profile;
  • keep the implementation language, framework, modules, and internal product architecture outside the generated requirements;
  • start a product through Runtime Protocol v1 and verify its externally visible OpenAPI, HTTP, explicit response obligations, and contracted SQLite boundaries;
  • invoke compiler products through Compiler Protocol v1 and verify declared artifacts, failure behavior, and deterministic fixpoints as black boxes;
  • invoke Decision Products through Decision Protocol v1 and verify positive, negative, and unknown Decision Results including Fact Gaps, explanation, scope, source provenance, deterministic source-justified Next Questions, independently evaluated Evidence Requirements and Rule-imposed Obligations, and the Rule Set Version selected only from an explicit Decision Date;
  • compile an optional authored Decision POST endpoint into OpenAPI 3.1 and verify the same Decision Results over HTTP through authored message schemas and bindings;
  • keep bootstrap provenance and implementation-neutral transformation obligations separate;
  • validate and publish the separated contract, decision-core, funding, and cloud-compliance vocabularies as bilingual WIDOCO references with a fixed Ontology Relationship Graph for each vocabulary and the SQL API example;
  • produce identical files for identical specs and compiler versions.

The prototype is not a complete SHACL, SQL, or OpenAPI compiler, a production deployment system, or an autonomous coding-agent orchestrator.

ADR 0016 accepts a bounded evolution toward Decision and Obligation Compilation. ADR 0017 implements its first compiler profile and source-pinned KfW 458 Applicant Eligibility Pilot; ADR 0018 adds explicit Fact Questions and Question Selection Conventions v1; ADR 0019 adds Evidence Evaluation Conventions v1; ADR 0020 adds Version Selection Conventions v1. ADR 0021 adds the cross-domain Cloud Privileged-Access Compliance Slice, a separate Cloud Compliance Domain Ontology, and Obligation Evaluation Conventions v1. The capability remains inside the Spec Compiler rather than becoming a second software system. ADR 0022 adds the optional KfW Decision HTTP Adapter without changing the applicant-eligibility Decision Contract. ADR 0023 separates the generic POST method type from the Decision HTTP Mapping v1 semantics. ADR 0024 replaces that fixed mapping with authored HTTP messages and body-pointer bindings.

2. Randbedingungen

Jede generierte Assertion benötigt eine explizite Spec-Aussage oder eine benannte, versionierte Konvention. Tests importieren keine Produktimplementierung. Toolchain und Product Bundles besitzen getrennte Umgebungen. Python, FastAPI und SQLite dürfen nicht aus dem Referenzprodukt auf andere Produktverträge übertragen werden.

Die Dokumentationspipeline benötigt zusätzlich Node für den lokal gepinnten Archify-Renderer; Java 17, WIDOCO und Graphviz bleiben für die Ontologiereferenzen bestehen. HTML ist die redaktionelle Quelle, JSON die Diagrammquelle; Markdown bleibt nur für kurze Repository-Einstiege und generierte Work Items.

2.1 Normative constraints

  • A generated requirement has exactly two permitted origins: an explicit product spec statement or a named, versioned convention.
  • Generated tests treat the product as a black box.
  • Handwritten product code, product dependencies, and product.toml belong to a Product Bundle; tool code and tool dependencies remain separate.
  • Generated files are outputs and must not be edited manually.
  • The repository architecture standard is defined in Dokumentationsstandard and loaded for coding agents through AGENTS.md.

3.1 Business context

The spec author records product intent. The Spec Compiler compiles it into deterministic guidance and proofs. A product developer or optional coding agent changes the separately bounded Generated Product. A reviewer or CI operator runs the same toolchain to decide whether the product conforms.

The coding agent is not programmatically orchestrated by the current prototype; the Work Graph, issue Markdown, and tests are a file-based handoff.

6.3 Evaluate a Decision Request

The KfW and cloud reference implementations read the compiled contract at runtime, but that is their implementation choice. Decision Protocol v1 exposes only JSON and process behavior. A missing Fact is a Fact Gap; it is never converted to false. A violated Condition takes precedence over gaps under Decision Conventions v1, so a source-backed ineligible result can remain determinate despite unrelated missing Facts. Question Selection Conventions v1 select the lowest-priority Fact Question among current Fact Gaps only while the result is unknown. Each invocation is stateless; the harness resubmits the accumulated complete Case rather than relying on a product session.

Evidence Evaluation Conventions v1 evaluate every Evidence Requirement after the Rule outcome has been derived. Applicability uses only its explicit Conditions. An applicable requirement is fulfilled only by matching Evidence with an explicit accepted Evidence Assessment; otherwise it is missing, and a non-applicable requirement is not_applicable. The evaluation exposes its own Source Citation and explanation. Neither Evidence nor its Assessment feeds back into Rule Condition Evaluations or the Decision Outcome. The JSON values are semantic identifiers and booleans, not a prescribed document representation, upload protocol, or storage boundary.

Obligation Evaluation Conventions v1 evaluate only Obligations explicitly imposed by a selected Rule. The Rule's Condition state becomes fulfilled, violated, or unknown, and the evaluation inherits the Rule Source Citation. This projection does not change the Decision Outcome or the independent Evidence Requirement Evaluation. Products with no authored Obligations return an empty list rather than inferred duties.

For the KfW product, the authored HTTP contract adds a second, independently started runtime path. The Contract Verification Harness reads the generated HTTP schemas and body bindings, starts the Decision HTTP Adapter through Runtime Protocol v1, and fetches /openapi.json. The adapter validates the request schema, extracts the contract input using the declared body pointer, and wraps and validates the result using the success-response declaration. It sends each authored Decision Request as JSON to POST /eligibility-decisions. The adapter uses the same evaluator as the Decision Product CLI; the generated proof compares complete results across the two interfaces. A valid ineligible or unknown result is HTTP 200; malformed or unsupported requests receive JSON HTTP 400, as explicitly authored in the KfW message resources. Other declared statuses, JSON media types, and body envelopes change the adapter and proof behavior. The adapter adds no UI, session, source fetch, or funding calculation.

6.4 Work Item execution

  1. A developer or coding agent selects a node whose dependencies are complete.
  2. It reads that node's goal, obligations, sources, exclusions, and test node.
  3. It changes only implementation-owned files in the Product Bundle.
  4. The named pytest node decides whether the Work Item is complete.
  5. The full test suite remains the final integration proof.

6.5 Bootstrap and verify the compiler product

G1 is a separately materialized source artifact with its own project metadata, lockfile, and manifest. Its implementation is deterministically derived from G0 by incrementing a generation marker and otherwise retaining the seed source. This establishes executable bootstrap continuity and a deterministic behavioral fixpoint, not an independent proof of compiler correctness.

Vollständige technische Details (bestehende englische Fassung)

Contract generation and verification run on one Windows or Linux development/CI host. Ontology documentation additionally deploys as a static GitHub Pages site; there is no Generated Product production deployment model yet.

  • The root and reference-product environments have separate dependency manifests and lockfiles.
  • The SQL Product Runtime and KfW Decision HTTP Adapter bind to the runner-supplied loopback host and port; the Decision Product CLI communicates through local standard streams.
  • On Windows the runner terminates the process tree with taskkill /T /F; on POSIX it uses a dedicated process group and signals the group.
  • Port selection has a small bind race; the runner retries early startup failure up to three times.
  • The Pages site is built from sources on every workflow run and is not stored in version control. Pull requests exercise the build without deployment.

Vollständige technische Details (bestehende englische Fassung)

8.1 Requirements provenance

Every generated assertion must be traceable to a spec statement or a versioned convention. Work Items carry human-readable sources. Unsupported ambiguity is a compiler error. The normative details are in Generierungsprinzipien.

8.2 Determinism

  • Spec filenames and Shape fields are sorted before rendering.
  • Valid fixture values follow fixed rules.
  • Issue prose comes from fixed templates.
  • JSON is rendered with stable insertion order and indentation.
  • No LLM or external service participates in compilation.
  • COMPILER_CONVENTIONS_VERSION, RUNTIME_PROTOCOL_VERSION, DECISION_CONVENTIONS_VERSION, DECISION_PROTOCOL_VERSION, and the Question Selection, Evidence Evaluation, Version Selection, and Obligation Evaluation and HTTP Contract convention versions expose semantic compatibility in generated artifacts.
  • Compiler Conventions v2 derive Decision Work Item IDs from the validated Product Bundle directory and prune stale Markdown only inside its generated/issues/ directory.
  • Compiler-product Work Graphs expose compiler_protocol_version and validated Bootstrap Process provenance; generated proofs compare consecutive output snapshots byte for byte. Bootstrap provenance does not prescribe the product implementation language.
  • WIDOCO reference output is explicitly excluded from byte-identity guarantees; its source vocabulary and public-term validation remain deterministic inputs.

8.3 Product isolation

Each product boundary consists of an explicit manifest and child process. The SQL profile combines OpenAPI/HTTP with named storage; the Decision profile uses one JSON request/result exchange over standard streams and may also declare a separate OpenAPI/HTTP adapter. The test language does not constrain the product language. Tool dependencies and reference-product dependencies are kept in separate environments.

8.4 Validation and error handling

The compiler rejects duplicate singleton values, unsupported datatypes or cardinalities, unsafe identifiers and paths, inconsistent relations, untraceable Rules, incomplete source identity, contradictory Conformance Cases, missing or multiply assigned Fact Questions, duplicate or non-positive question priorities, an invalid Question Flow Case, missing or contradictory Evidence Expectations, unknown Evidence Requirements, duplicate Evidence Assessments, invalid Evidence types, missing or contradictory Obligation Expectations, unknown or multiply owned Obligations, missing Decision Dates, overlapping or uncovered Rule Set Version validity, multiple or mismatched Decision POST endpoints, invalid or unsupported HTTP schemas, duplicate JSON schema keys, missing message declarations, invalid body pointers, unsupported path/media/status values, ambiguous profile selection, unknown placeholders, and protocol-version mismatches. Runtime failures include captured process output. OpenAPI is validated before subset comparison; Decision Results must be JSON objects.

8.5 Generated artifacts

Specs and versioned conventions are inputs. Expected OpenAPI and/or the compiled Decision Contract, tests, Work Graph, and issues are outputs and carry generated-file warnings where appropriate. Changes are made at the source and regenerated.

The WIDOCO references, legacy WebVOWL output, and Ontology Relationship Graph under build/ontology-site/ are disposable, unversioned documentation artifacts. The canonical ontology and Product Bundle specs remain the authored sources. The site root contains the documentation overview. The Ontology Relationship Graph and its self-hosted Cytoscape.js asset live at /ontologies/. /graph/ is a compatibility redirect to /ontologies/ that preserves query parameters and fragments; contextual references and RDF paths stay unchanged.

8.6 Security and trust

product.toml can execute arbitrary local commands under either product protocol. The runners are intended only for trusted repositories and Product Bundles. OpenAPI references are local, the test server uses loopback networking, and test databases are temporary files.

8.7 Architecture documentation

arc42, C4, and ADRs use the same element names and are updated in the same change as architecture-significant code. Dokumentationsstandard defines the review rules, while AGENTS.md loads them into Codex workflows.

8.8 Decision and obligation semantics

The Decision and Obligation Compilation roadmap defines the current and target semantics and ontology boundaries. The first profile implements requiresAllRules through Decision Conventions v1. Missing Case Facts produce explicit Fact Gaps and may produce an unknown Decision Outcome. Question Selection Conventions v1 then select at most one explicit, source-justified Next Question from those current gaps. A client resubmits the complete accumulated Case through the unchanged Decision Protocol v1 boundary. Evidence Evaluation Conventions v1 independently evaluate explicitly sourced Evidence Requirements. All applicability Conditions must be satisfied; matching Evidence fulfills an applicable requirement only with an explicit accepted Evidence Assessment. The resulting status, Evidence classifications, explanation, and separate source provenance are added to the Decision Result without changing Condition truth or the Decision Outcome. Obligation Evaluation Conventions v1 project each explicitly Rule-imposed Obligation from its Rule Condition: satisfied becomes fulfilled, violated remains violated, and unknown remains unknown. Evaluations include the Obligation text and inherited Rule provenance. Neither Obligations nor Evidence are inferred from domain vocabulary. Version Selection Conventions v1 then select exactly one Rule Set Version from the stable Rule Set, explicit Decision Date, and authored half-open Validity Periods. Version identity and validity Source Citation are compilation inputs; the selected identity, label, and date are result fields. Requests cannot select a version and no wall-clock/latest default exists. Missing dates, gaps, and overlaps fail; generated Decision-product and Compiler-product black-box tests exercise the historical boundary and ambiguity diagnostics. Ambiguous Specs, conflicting Facts, ambiguous Rule Set Version applicability, and incompatible entailed outcomes remain errors. External Source Revisions are reached through Source Citations in authored Specs and do not bypass ADR 0001's permitted requirement origins.

A Rule Set Version's version Source Citation establishes identity and validity; Rules and Evidence Requirements may cite different immutable Source Revisions. This permits the cloud policy Rules to cite NIST SP 800-53 while their assessment Evidence Requirement cites NIST SP 800-53A without weakening traceability.

10. Qualitätsanforderungen

Beobachtbare Szenarien prüfen fehlende Anforderungen, deterministische Outputs, Produktfreiheit, Fehlerdiagnosen, Prozess-Cleanup und Provenance. Für die Website kommen hinzu: Links funktionieren unter einem Repository-Präfix, Suche erreicht Dokumente und Diagrammknoten, Theme ist konsistent, und fehlerhafte lokale Quellen ersetzen den letzten gültigen Build nicht.

11. Risiken und technische Schulden

G0/G1-Kontinuität ist keine unabhängige Oracle. Referenzprodukte, Generator und Nachweise teilen Konventionen; rechtliche oder sicherheitstechnische Vollständigkeit folgt daraus nicht. Manuell kuratierte KfW- und NIST-Aussagen benötigen fachliche Review. Das Manifest kann vertrauenswürdige lokale Befehle ausführen.

Die HTML-Migration verzichtet auf eine parallele Markdown-Wahrheit. Der lokal gepinnte Archify-Fork erhöht den Wartungsbedarf bei Updates, insbesondere für den deutschen Katalog und Theme-Bridge. WIDOCO bleibt eine gesonderte Referenzansicht; ein Quick Build erneuert seine fachlichen Inhalte nicht.

Vollständige technische Details (bestehende englische Fassung)
Risk or debt Consequence / mitigation
The public ontology currently defines only the vocabulary slice exercised by the prototype. Publication validation prevents undefined used terms, but OWL axioms and bilingual descriptions must deepen as the contract language grows.
Exactly one endpoint, table, parameter, and shared Shape are supported. The model has not demonstrated multi-resource scaling. Extend only with explicit new semantics and tests.
The SQL profile's Explicit Obligation Model remains an untyped dictionary in a large generator module. Renderer drift remains possible in that profile; use the typed immutable decision model as evidence for a later safe migration, not as permission for an unrelated rewrite.
Expected OpenAPI and tests come from the same compiler. A shared interpretation bug can affect both oracle and proof; add independent conformance examples or mutation tests.
G1 is mechanically derived from G0 and judged by tests generated from the same lineage. The bootstrap proves executable continuity and determinism but not semantic independence; retain G0 as a trust anchor and add an independent compiler or oracle before claiming diverse double compilation.
Experimental IRIs contain the GitHub account and repository name. Renaming either breaks identifiers; migrate through a persistent redirect such as w3id.org before promising stable public IRIs.
WIDOCO/WebVOWL remain documentation-build dependencies with older bundled browser assets. Pin and hash-check WIDOCO, retain the legacy URLs, and keep the build outside product runtime boundaries.
Graphviz and Cytoscape.js versions affect the published graph. Require dot in CI, sort layout input, hash-check and self-host Cytoscape.js, and test graph output and fixed viewport behavior before publishing.
GitHub Pages has no RDF content negotiation or SPARQL service. Publish explicit HTML and serialization URLs; add dynamic infrastructure only if a demonstrated use case requires it.
OpenAPI comparison intentionally supports a narrow 3.1 profile. Equivalent composed schemas may be rejected; broaden the comparator only with explicit semantics and regression tests.
HTTP Contract Conventions v1 supports one fixed POST path, required JSON bodies, explicit schemas, one 2xx and one 4xx response, and object body-pointer bindings. Other methods, multiple operations, optional bodies, non-JSON transports, schema references, and general schema equivalence require explicit later support.
Authored HTTP schemas and Decision semantics can drift. Generated case validation and CLI parity detect covered inconsistencies; update both specs when the interface or facts change and retain independent review beyond the finite cases.
Integer Shape fields have a mapping but no deterministic fixture synthesizer. Such fields fail late in fixture generation; either implement the value rule or reject them earlier.
Generated issue cleanup removes only stale Markdown directly below a Product Bundle's generated/issues/. A wider cleanup could destroy authored data; keep the target fixed and derived from the validated Product Bundle.
Generation writes several files non-atomically. An interrupted run can leave mixed versions; consider staging then atomic replacement.
Free-port selection has a time-of-check/time-of-use race. Three startup attempts reduce but do not eliminate rare parallel-run collisions.
Runtime Protocol v1 executes arbitrary commands. Use only trusted bundles; sandboxing is outside the prototype.
Direct SQLite access is intentionally part of this contract profile. It excludes opaque or remote storage implementations unless the technical contract and verifier evolve.
Portability is locally tested but has no visible OS CI matrix. Add Windows and Linux CI jobs before claiming production-grade portability.
Unknown identifiers and other error behavior are unspecified. Implementations may differ; add explicit specs rather than inferred 404 behavior if needed.
External program documents change independently of the repository. Pin Source Revisions by identifier, declared validity, retrieval date, and content identity; never infer a latest version.
A scoped positive applicant result may be mistaken for funding approval or advice. Name the Decision precisely, retain its exclusions in every presentation, and never claim legal entitlement or provider approval.
Two domains still provide limited evidence for a reusable ontology. Keep Funding and Cloud Compliance Domain Ontology terms separate; require equivalent semantics in further domains plus an ADR before any promotion.
Decision Conventions v1 supports only boolean Conditions combined by requiresAllRules. Reject disjunctions, numeric rules, and unmodeled aggregation instead of approximating them; add a new versioned convention when another project demonstrates semantics.
The compiler and generated tests share the same Decision Conventions implementation. Authored eligible, ineligible, and unknown Conformance Cases catch disagreement with the Spec, but an independent oracle is still required before claiming formal correctness.
Question priorities are static authored policy. The order is reproducible but not optimized for cost, information gain, audience, or branching probability; introduce richer selection semantics only through an explicit later convention.
The compiler, Decision Product reference implementation, and generated proof share Question Selection Conventions v1. The authored Question Flow Case and negative-with-gap proof catch observable disagreement, but an independent implementation is still needed before claiming semantic diversity.
The compiler, Decision Product reference implementation, and generated proof share Evidence Evaluation Conventions v1. Authored cases cover all three requirement statuses and a rejected-Evidence mutation, but an independent implementation is still needed before claiming semantic diversity.
The compiler, cloud reference implementation, and generated proof share Obligation Evaluation Conventions v1. Authored cases cover all three statuses and explicit provenance, but the convention supports only projection from one Rule Condition; add independent implementations and richer sourced cases before modeling lifecycle or compound applicability.
Evidence Assessment is explicit input, not automatic document validation. A result reports the supplied assessment semantics only; never imply document authenticity or content correctness, and add ingestion or validation only through a sourced later contract.
The KfW source statement is manually curated. The compiler proves identity and traceability, not transcription completeness or legal correctness; retain human review and the scope note.
The NIST source statements are manually curated and the cloud slice covers only IA-2 and IA-2(1). The compiler proves pinned identity and traceability, not assessment completeness or security; retain expert review and the explicit scope note.
Authored Rule Set Version intervals may contain gaps or accidental overlaps. The compiler rejects overlaps globally and rejects any Conformance Case or runtime request whose Decision Date selects zero or multiple versions; no latest-version fallback masks catalogue defects.
