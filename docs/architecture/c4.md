# SHACL Contract Toolchain – C4 model

This document applies the [C4 model](https://c4model.com/) to the current
prototype. It deliberately separates three concepts:

1. the executable **SHACL Contract Toolchain**,
2. the static **Product Workspace**, and
3. the separately executable **Generated Product**, and
4. the toolchain's static **Toolchain Self-Description Bundle**.

The diagrams use Mermaid because C4 is notation-independent. Every box states
its C4 element type, responsibility, and—below System Context—technology. Solid
arrows are unidirectional relationships labeled with the actual interaction.

## Level 1: System Context

Scope: the SHACL Contract Toolchain and its direct users and neighboring
software systems. Audience: everybody involved in specifying, implementing, or
reviewing products.

```mermaid
flowchart LR
    author["Person: Spec Author / Product Developer<br/>Defines product intent and owns implementation choices"]
    reviewer["Person: Reviewer / CI Operator<br/>Runs reproducible generation and verification"]
    tool["Software System: SHACL Contract Toolchain<br/>Compiles specs into guidance and verifies products as black boxes"]
    agent["External Software System: AI Coding Agent (optional)<br/>Consumes file-based work guidance; not currently orchestrated"]
    product["External Software System: Generated Product<br/>Implements the explicit HTTP, data, and storage contract"]

    author -->|"provides specs and selects product implementation"| tool
    reviewer -->|"starts generation and verification"| tool
    tool -->|"provides Work Graph, issues, and proofs via files"| agent
    agent -->|"changes implementation-owned product files"| product
    author -->|"may implement without an AI agent"| product
    tool -->|"starts and verifies through declared external boundaries"| product
    tool -->|"invokes itself through Compiler Protocol v1 and verifies generated files"| tool

    classDef person fill:#f6f6f6,stroke:#555,color:#111;
    classDef system fill:#1168bd,stroke:#0b4884,color:#fff;
    classDef external fill:#999,stroke:#666,color:#fff;
    class author,reviewer person;
    class tool system;
    class agent,product external;
```

Legend:

| Style | C4 type |
| --- | --- |
| Blue | Software System in scope |
| Gray | External Software System |
| Light gray | Person |

The AI Coding Agent is conceptual and optional. Today the toolchain creates a
file-based handoff; it does not invoke an agent API.

Compiler products are replaceable roles, not a dedicated product class. Their
specs separate the general Software Application, its Compiler Protocol
conformance, and the Transformation Contract it implements.

## Level 2: Container view

### SHACL Contract Toolchain

Scope: executable applications and data stores inside the SHACL Contract
Toolchain. The Generated Product remains an external software system.

```mermaid
flowchart LR
    author["Person: Spec Author / Product Developer<br/>Authors specs and product-owned files"]

    subgraph tool_boundary["Software System: SHACL Contract Toolchain"]
        compiler["Container: Contract Compiler CLI<br/>Python 3.12, RDFLib<br/>Builds one Contract Model and renders deterministic outputs"]
        harness["Container: Contract Verification Harness<br/>Python 3.12, pytest, HTTPX, pySHACL, OpenAPI Spec Validator<br/>Executes generated black-box proofs"]
        workspace[("Container / Data Store: Product Workspace<br/>File system: products/&lt;name&gt;/<br/>Stores authored product files and generated artifacts; not executable")]
        selfdesc[("Container / Data Store: Toolchain Self-Description Bundle<br/>File system: products/shacl_contract_toolchain/<br/>Stores compiler specs, manifest, and generated proofs")]
    end

    product["External Software System: Generated Product<br/>Technology selected by product implementer<br/>Runs separately and exposes contracted boundaries"]

    author -->|"writes Turtle specs, manifest, and implementation files"| workspace
    author -->|"starts via Poe / uv"| compiler
    author -->|"starts via Poe / uv"| harness
    compiler -->|"reads specs/*.ttl"| workspace
    compiler -->|"writes expected OpenAPI, tests, Work Graph, and issues"| workspace
    compiler -->|"reads compiler specs and writes generated proofs"| selfdesc
    harness -->|"loads manifest, specs, generated tests, and expected OpenAPI"| workspace
    harness -->|"starts/stops via Runtime Protocol v1; verifies via HTTP and contracted storage"| product
    harness -->|"invokes compiler via Compiler Protocol v1 and compares generated files"| compiler
    harness -->|"loads compiler manifest and generated proofs"| selfdesc

    classDef person fill:#f6f6f6,stroke:#555,color:#111;
    classDef container fill:#438dd5,stroke:#1f5f99,color:#fff;
    classDef datastore fill:#2e75b6,stroke:#1f5f99,color:#fff;
    classDef external fill:#999,stroke:#666,color:#fff;
    class author person;
    class compiler,harness container;
    class workspace,selfdesc datastore;
    class product external;
```

Legend:

| Style | C4 type |
| --- | --- |
| Medium blue box | Executable Container inside the toolchain |
| Blue cylinder | Data-store Container; file-based artifact store, not an application |
| Gray box | External Software System |
| Light gray box | Person |

Poe is command orchestration, not a Container. `tools/contract_runtime.py` and
`tools/compiler_runtime.py` are Components inside the pytest process, not
separately running Containers. The self-relationship in the System Context is
the explicit bootstrap interaction; it does not claim an independent compiler.

### SQL API Example product

Scope: runtime Containers of the Generated Product represented by
`sql_api_example`. Static specs, manifests, source files, and generated files are
not runtime Containers.

```mermaid
flowchart LR
    harness["External Software System: SHACL Contract Toolchain<br/>Starts and verifies the product"]
    workspace[("External Artifact Store: Product Workspace<br/>Product source, specs, manifest, and generated artifacts")]

    subgraph product_boundary["Software System: Generated Product – SQL API Example"]
        runtime["Container: Product Runtime<br/>Python, FastAPI, Pydantic, Uvicorn<br/>Publishes OpenAPI and GET /articles/{id}"]
        database[("Container / Data Store: Contracted Data Store<br/>SQLite<br/>Stores the articles table")]
    end

    harness -->|"reads product.toml and starts declared command"| workspace
    workspace -->|"provides implementation code to the declared command"| runtime
    harness -->|"GET /openapi.json and GET /articles/{id} over loopback HTTP"| runtime
    harness -->|"inspects schema and inserts deterministic fixtures via SQLite"| database
    runtime -->|"initializes schema and reads articles via SQLite"| database

    classDef container fill:#438dd5,stroke:#1f5f99,color:#fff;
    classDef datastore fill:#2e75b6,stroke:#1f5f99,color:#fff;
    classDef external fill:#999,stroke:#666,color:#fff;
    class runtime container;
    class database datastore;
    class harness,workspace external;
```

Legend:

| Style | C4 type |
| --- | --- |
| Medium blue box | Product application Container |
| Blue cylinder | Product data-store Container |
| Gray box/cylinder | Supporting element outside the product boundary |

FastAPI and Python describe only this reference Product Runtime. A different
Generated Product may use any implementation technology compatible with Runtime
Protocol v1 and its explicit product specs.

## Level 3: Component views


### Contract Verification Harness

Scope: components executing inside the pytest-based Contract Verification
Harness Container.

```mermaid

    runtime["External Software System: Generated Product<br/>Separately running Product Runtime"]
    compiler_product["External Container: Contract Compiler CLI<br/>Invoked as the Compiler Product under test"]
    database[("External Data Store: Contracted Data Store<br/>SQLite in the reference contract")]

    subgraph harness_boundary["Container: Contract Verification Harness – Python 3.12 / pytest"]
        suite["Component: Generated Contract Test Suite<br/>pytest<br/>Coordinates focused executable proofs"]
        adapter["Component: Product Runtime Adapter<br/>subprocess, HTTPX<br/>Starts, probes, retries, and cleans process trees"]
        compiler_adapter["Component: Compiler Runtime Adapter<br/>subprocess, TOML<br/>Invokes compiler products and captures exit status and output"]
        api["Component: OpenAPI Verifier<br/>OpenAPI Spec Validator + generated comparator<br/>Validates 3.1 and required contract subset"]
        sql["Component: SQLite Contract Verifier<br/>Python sqlite3<br/>Checks schema and inserts deterministic fixtures"]
```

## Code level

A C4 Code diagram is intentionally omitted. The compiler and runner are small,
and function-level details are already visible in source and in the Component
views. A Code diagram should be added only if a stable internal model emerges
whose relationships are not evident from the code.

## Artifact classification

This table prevents static files from drifting into C4 diagrams as fictitious
application Containers.

| Artifact | Classification | Executable C4 Container? |
| --- | --- | ---: |
| `specs/*.ttl` | Authored static input | No |
| `product.toml` | Static Runtime Protocol adapter | No |
| Compiler-product `product.toml` | Static Compiler Protocol v1 adapter | No |
| `products/shacl_contract_toolchain/` | Static Toolchain Self-Description Bundle | No |
| `app.py` or alternative product source | Source artifact | No; only the started Product Runtime is a Container |
| `tests/test_contract.py` | Generated source loaded into the pytest Container | No |
| `generated/expected-openapi.json` | Generated static contract | No |
| `generated/work-graph.json` | Generated static work description | No |
| `generated/issues/*.md` | Generated static work instructions | No |
| `/openapi.json` | Runtime HTTP resource | No |
| SQLite database file | Persistent store | Yes, as a C4 data-store Container |

## Model maintenance

The rules in [maintenance.md](maintenance.md) are normative. In particular:

- preserve the system boundary between SHACL Contract Toolchain and Generated
  Product;
- keep the canonical names used in this document;
- update relationships and technologies in the same change as code;
- do not present the optional AI Coding Agent as an automated integration until
  such orchestration exists;
- do not add conceptual product layers that are absent from the implementation.
