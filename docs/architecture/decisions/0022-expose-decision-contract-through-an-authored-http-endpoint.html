ADR 0022: Expose an authored Decision Contract through an HTTP endpoint

Status

Accepted. This extends ADR 0017 without changing Decision Protocol v1.

Context

The KfW 458 Applicant Eligibility Pilot already compiles one source-backed Decision Contract and verifies a JSON standard-stream process. A browser client needs an HTTP boundary, but the SQL API profile describes one GET endpoint and one SQLite table. Treating that profile as a general decision API would invent storage and GET semantics. An HTTP adapter also needs an explicit, testable request and response contract rather than a path chosen only in product code.

Decision

  • Add sco:HttpEndpoint as the shared superclass of the existing sco:GetEndpoint and new sco:DecisionPostEndpoint. A Decision POST endpoint explicitly names its path, JSON media type, success and invalid-request statuses, and the sdo:DecisionContract it exposes.
  • Define Decision HTTP Mapping v1, selected by dcterms:conformsTo sco:DecisionHttpMappingV1. It supports exactly one fixed POST path per Decision Product, application/json, HTTP 200 for every valid Decision Result (eligible, ineligible, or unknown), and HTTP 400 with a nonempty JSON error string for an invalid Decision Request.
  • The POST body is the existing Decision Request JSON: contract identity, stable Rule Set identity, and ISO Decision Date are required; case and evidence are optional. Fact fields compiled from Rule and Evidence applicability JSON Pointers are optional booleans, preserving Fact Gaps. Caller-selected Rule Set Versions are forbidden. The 200 body is the full Decision Result, including selected version, evaluations, Next Question, provenance, and scope note. The mapping does not change decision semantics.
  • Compile the authored endpoint and typed Decision Contract into a self-contained OpenAPI 3.1 document, generated HTTP black-box tests, and a Work Item. The document is published at /openapi.json through Runtime Protocol v1. The tests compare its supported schema subset and send every authored Conformance Case through HTTP, checking parity with the separately verified Decision Protocol v1 result and invalid-request handling.
  • Keep the existing CLI adapter and generated Decision Contract unchanged. The KfW reference Product Bundle supplies an additional HTTP adapter through a [runtime] section of product.toml; both adapters use the same evaluator. The compiler generates contracts and proofs, not executable server code.
  • Keep UI layout, sessions, funding amount calculation, document upload, and implementation technology outside this endpoint and the pilot scope.

Consequences

  • A client can call the KfW applicant decision over HTTP without changing the meaning of eligible or the source-backed rule versions.
  • The Decision Product can still be verified through its original process protocol, while its optional HTTP surface has a separate explicit contract.
  • The compiler's decision profile gains an optional HTTP projection. A Decision POST endpoint without a Decision Product, multiple endpoints, an unmatched Decision Contract, or unsupported path/media/status values fail compilation.
  • The generated OpenAPI schema is intentionally limited to direct schemas and local references, with a root not constraint rejecting caller-selected versions. Richer HTTP operations or schema composition require a later mapping.

Alternatives

  • Reuse sco:GetEndpoint and its SQL reader. Rejected because it requires a table and cannot express a JSON POST decision request.
  • Handwrite OpenAPI independently of the Decision Contract. Rejected for this reference slice because its request pointers, outcomes, and result fields would duplicate the compiled source of truth.
  • Replace Decision Protocol v1 with HTTP. Rejected because the existing technology-neutral decision boundary and its black-box proofs remain useful.
