ADR 0023: Separate the POST method from Decision HTTP Mapping

Status

Accepted. Supersedes the endpoint-class choice in ADR 0022. The HTTP behavior, Decision Contract, and other decisions in ADR 0022 remain in force.

Context

ADR 0022 introduced both sco:DecisionPostEndpoint and the explicit, versioned sco:DecisionHttpMappingV1. The class combines the HTTP method with Decision semantics, while the mapping already names and defines those semantics. This duplicates one concern in two vocabulary terms and makes a method-only POST endpoint impossible to describe with the shared vocabulary. The KfW endpoint is a product resource; its reusable vocabulary belongs in the shared SHACL Contract Ontology.

Decision

  • Replace sco:DecisionPostEndpoint with generic sco:PostEndpoint, a subclass of sco:HttpEndpoint. Its class membership states only the HTTP method.
  • The KfW product endpoint declares both a sco:PostEndpoint and dcterms:conformsTo sco:DecisionHttpMappingV1. Only the versioned mapping defines Decision Request, Decision Result, and HTTP status behavior.
  • The Decision Contract Reader requires both declarations for the optional Decision HTTP projection. A mapping without the POST type, a POST endpoint without the supported mapping, or multiple candidate endpoints fails compilation. The current compiler does not implement other POST mappings.
  • Give sco:exposesDecisionContract and sco:invalidRequestStatus the general sco:HttpEndpoint domain. Their allowed values and Decision-specific meaning are validated by the compiler convention, not inferred from RDFS domains.

Consequences

  • The shared ontology names the method independently of any product or API domain. A future mapping can reuse sco:PostEndpoint without another method-and-domain class.
  • The KfW HTTP path, JSON contract, generated OpenAPI, runtime behavior, and black-box proofs keep their existing meaning. The product spec and compiler change together, and G1 is regenerated from G0.
  • Specs still using sco:DecisionPostEndpoint must migrate to the generic type and the explicit mapping; silent fallback to Decision Protocol v1 is not a supported migration path.

Alternatives

  • Keep sco:DecisionPostEndpoint. Rejected because its Decision meaning duplicates sco:DecisionHttpMappingV1.
  • Infer POST solely from the mapping and omit an endpoint type. Rejected because method and mapping are separate declarations that the compiler can verify.
  • Define kfw458:PostEndpoint in the product namespace. Rejected because POST is a reusable HTTP method; the concrete KfW endpoint instance already lives in the product namespace.
