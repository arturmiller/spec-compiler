ADR 0024: Author HTTP messages and bindings in product specs

Status

Accepted. Supersedes the fixed Decision HTTP Mapping v1 choice in ADR 0022 and the mapping-selection requirement in ADR 0023. The generic POST type and separate Decision Protocol v1 remain in force.

Context

The previous compiler recognized the exact sco:DecisionHttpMappingV1 IRI and built a predetermined HTTP request, result, error schema, status pair, and tests. Moving that IRI into a product namespace would leave the actual API definition in compiler code. The product needs to own its concrete wire contract, while the shared ontology should provide reusable vocabulary.

Decision

  • Remove the named Decision HTTP mapping and its dispatch. The SHACL Contract Ontology supplies generic HTTP endpoints, requests, responses, body schemas, media types, statuses, body pointers, and contract invocation relations.
  • The KfW http_api.ttl explicitly declares the endpoint and three message resources. Endpoint and messages must be named resources for deterministic provenance. sco:bodySchema holds an authored JSON Schema Draft 2020-12 value as an rdf:JSON literal. JSON Schema describes the actual JSON wire contract directly; the existing SQL SHACL profile remains available separately.
  • Define HTTP Contract Conventions v1 for these general vocabulary semantics. sco:request, sco:successResponse, and sco:invalidRequestResponse give each message its role. sco:bodyPointer selects contract input from the request and locates the result or error text in the corresponding response. The empty pointer denotes the entire body; other pointers describe object envelopes. sco:invokesContract names the invoked contract.
  • The HTTP Contract Reader validates declarations and the supported schema subset. The OpenAPI Contract Renderer copies authored schemas and HTTP values without adding Decision fields. It also renders x-spec-compiler-binding metadata consumed by the reference adapter; equivalent implementations need not publish that extension.
  • Keep one POST operation with a required JSON body, one body-bearing 2xx success response, and one 4xx invalid-request response in the current profile. JSON media types can differ between messages. Missing statements, unsupported schema keywords or formats, schema references, invalid pointers, and ambiguous response roles fail compilation.
  • The product integration currently invokes Decision Protocol v1 contracts. The Decision Contract Reader checks that the explicit invoked contract is the product's Decision Contract. HTTP parsing and rendering themselves have no product-resource or mapping-IRI dispatch.
  • Generate HTTP proofs from authored message schemas and bindings. The explicit invocation relation also justifies testing all Decision Conformance Cases and comparing the extracted result with the CLI result. Invalid-body tests derive from schema constraints and malformed JSON, without KfW field names, fixed status codes, or implementation-specific error messages.
  • Declare jsonschema in the toolchain, G1, and KfW product environments. It validates schemas during compilation and observed bodies during tests; the reference adapter uses it for request and response validation. This is an implementation dependency, not a product-contract requirement.

Consequences

  • Changing product schemas, paths, JSON media types, success/error status codes, or body envelopes changes generated OpenAPI, proof expectations, and the reference adapter's behavior. A mutation test changes only the specs, renames their HTTP resources, and runs generated black-box proofs against the same backend implementation.
  • The default KfW API keeps its existing path, JSON body shapes, and 200/400 responses. Its JSON schemas are now maintained explicitly in the product. They can drift from Decision semantics; generated case validation and CLI parity provide checks, but the finite cases are not a completeness proof.
  • The supported schema keywords and structural comparison rules are documented in the generation principles. The compiler does not fetch schema references or claim general JSON Schema logical equivalence. Additional methods, multiple operations, optional bodies, and non-JSON transports need further explicit support.
  • The old mapping term and sco:exposesDecisionContract are removed from the experimental shared vocabulary; the product uses sco:invokesContract and explicit messages. Historical ADRs retain the superseded design.

Alternatives

  • Move DecisionHttpMappingV1 into the KfW namespace while retaining special compiler code. Rejected because the API definition would still be implicit.
  • Keep generating complete HTTP schemas from the Decision Contract. Rejected because the product could not independently describe its HTTP wire contract.
  • Introduce another vocabulary for every JSON Schema keyword. Rejected because JSON Schema already describes nested JSON objects, arrays, unions, and constraints without duplicating the standard in the shared ontology.
  • Handwrite an unrelated OpenAPI document. Rejected because the authored HTTP bindings and the executable proofs should continue to share one spec source.
