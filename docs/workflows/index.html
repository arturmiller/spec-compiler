Laufzeit und Nachweise

Vom Vertrag zum beobachtbaren Ergebnis

Die Kompilierung liest autorisierte Specs. Der Contract Verification Harness startet anschließend Produkte und beobachtet ihr Verhalten. Eine Next Question entsteht bei einer Decision-Auswertung, nicht beim Einlesen der Specs.

1. Specs kompilieren

Die sortierten Turtle-Dateien eines Product Bundle werden zusammengeführt, auf Eindeutigkeit geprüft und in das zuständige Explicit Obligation Model oder Explicit Decision and Obligation Model überführt. Deterministische Renderer erzeugen Verträge, Tests und Work Items. Fehlende Spec-Angaben werden nicht durch Fragen an Produktnutzer ersetzt: Sie sind Kompilierungsfehler.

2. Ein Produkt prüfen

Runtime Protocol v1 deklariert, wie ein Produkt gestartet wird. Der Harness wartet auf OpenAPI, prüft Schnittstelle und Verhalten, kontrolliert gegebenenfalls die explizit verlangte SQLite-Speicherung und beendet den vollständigen Prozessbaum. Die Implementierung wird nicht importiert.

3. Einen Decision Request auswerten

Ein Decision Request nennt Contract, stabiles Rule Set, Decision Date und Case Facts. Das Decision Product wählt die ausdrücklich gültige Rule Set Version und wertet ihre Rules aus. Fehlende Facts werden als Fact Gaps ausgewiesen. Nur ein noch undeterminiertes Resultat trägt die nach expliziter Priorität ausgewählte Next Question.

Der Client ergänzt die Antwort im vollständigen Case und sendet einen neuen Request. Evidence Requirements und Rule-imposed Obligations werden getrennt ausgewertet; ihre Ergebnisse ändern weder Condition truth noch den Decision Outcome.

Die Zustandsansicht zeigt positive, negative und undeterminierte Ergebnisarten eines einzelnen Aufrufs, keine Sitzung. Die Specs benennen konkrete Outcomes, zum Beispiel eligible / ineligible oder compliant / non_compliant.

4. Den Compiler als Produkt prüfen

G0 materialisiert G1 aus dem deklarierten Seed. Generierte Black-Box-Nachweise starten G1 über Compiler Protocol v1 und vergleichen zwei Kompilierungen derselben Fixtures byteweise. Das prüft ausführbare Kontinuität und Determinismus; eine unabhängige fachliche Oracle ersetzt es nicht.

5. Die Dokumentation veröffentlichen

HTML-Quellen, Diagrammmodelle und Ontologien werden als abgeleitete Website zusammengeführt. Die lokale Vorschau verwendet dieselben Quellen. GitHub Actions prüft den vollständigen Workflow und veröffentlicht den statischen Build nach einem Push auf main. Pull Requests bauen ohne Veröffentlichung.

Details zu Protokollen und unterstützten Konventionen stehen in den Generierungsprinzipien; ihre Architekturgrenzen in arc42.
