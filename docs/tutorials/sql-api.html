Tutorial 1 · vollständiger Einstieg

Eine Datenbedingung bis zum laufenden Produkt verfolgen.

Dieses Beispiel zeigt, wie eine ausdrücklich verlangte Artikelbeschreibung in Vertragsdatei, Test und Produktverhalten erscheint. Python/FastAPI sind die Wahl dieses Beispiels, nicht die Vorgabe des Compilers.

Ziel und Grenzen

Das SQL-Profil beschreibt einen GET-Endpunkt, eine ausdrücklich verlangte SQLite-Tabelle und eine gemeinsame Shape. Dieses Tutorial modelliert keine allgemeinen CRUD-Operationen und macht SQLite nicht zur Pflicht für andere Profile. Profilgrenzen · Shape im Glossar.

1. Ein eigenes Übungsprodukt anlegen

Alle folgenden Befehle beginnen im Repository-Root.

uv run --extra dev python tools/tutorial_workspace.py sql-api
uv run --extra dev python tools/generate.py --product products/tutorial_sql_api_example

Das neue Product Bundle enthält verfasste Specs, Implementierung, Produktmanifest und eigene Abhängigkeiten. Der Compiler erzeugt die zuvor ausgelassenen Verträge und Tests.

2. Die beiden Spec-Dateien lesen

article_shape.ttl beschreibt Artikel, Beschreibung und Preis. Die Beschreibung ist ein erforderlicher String mit Mindestlänge 1; der Preis ist eine Dezimalzahl größer als 0 und kleiner als 1 000 000. Die Shape ist geschlossen. system_contract.ttl verbindet GET-Endpunkt, Parameter, Antwort und SQLite-Speicherung.

sh:path article:description ;
sh:datatype xsd:string ;
sh:minCount 1 ;
sh:maxCount 1 ;
sh:minLength 1 ;

Die Bedingungen stammen aus der Spec. Die Beispielimplementierung ist nicht ihre Quelle.

3. Ausgaben und Startgrenze anschauen

In products/tutorial_sql_api_example/generated/expected-openapi.json steht das geforderte minLength: 1. Der generierte Test enthält die abgeleiteten Verpflichtungen und einen gültigen Testdatensatz. work-graph.json und die Issue-Texte nennen Quellen, Abhängigkeiten und einzelne Nachweise.

product.toml benennt den Startbefehl und die vom Harness gelieferten Host-, Port- und Datenbankwerte. Die Referenzimplementierung läuft als eigener FastAPI-Prozess und liest SQLite. Die Tests importieren ihren Code nicht.

4. Das laufende Produkt prüfen

uv run --extra dev pytest -q products/tutorial_sql_api_example/tests

Erwartung: Die Nachweise bestehen. Der Harness startet den echten Prozess, holt OpenAPI, prüft Schema und deklarierte SQLite-Grenze, schreibt einen Testdatensatz und ruft den GET-Endpunkt auf. Danach beendet er auch mögliche Kindprozesse.

5. Die Anforderung verschärfen

Ändere ausschließlich im Übungsprodukt specs/article_shape.ttl die Mindestlänge der Beschreibung von 1 auf 3. Regeneriere:

uv run --extra dev python tools/generate.py --product products/tutorial_sql_api_example
uv run --extra dev pytest -q products/tutorial_sql_api_example/tests

Jetzt enthalten Vertrag und Nachweise minLength: 3; die erzeugte gültige Beschreibung ist xxx. Die unveränderte Beispielimplementierung veröffentlicht jedoch noch Mindestlänge 1. Deshalb soll der OpenAPI-Nachweis zunächst scheitern. Das ist die sichtbare Wirkung einer Spec-Änderung, kein Anlass, den generierten Test abzumildern.

6. Nur die Implementierung nachziehen

In products/tutorial_sql_api_example/app.py verlangt das Beispielmodell nun dieselbe Mindestlänge:

description: Annotated[str, Field(min_length=3)]

Diese konkrete Pydantic-Zeile gehört nur zu dieser Beispieltechnologie. Eine andere Implementierung müsste denselben äußeren Vertrag erfüllen, nicht denselben Code verwenden.

uv run --extra dev pytest -q products/tutorial_sql_api_example/tests

Erwartung: Die Nachweise bestehen wieder. Spezifikation, erwartete Schnittstelle und laufendes Verhalten sind konsistent.
