Tutorial 2 · Decision und explizites HTTP

Eine begrenzte Decision auswerten und ihre HTTP-Abbildung ändern.

Nach dem SQL-Einstieg betrachten wir ein anderes Profil: Das Produkt wertet Regeln für gelieferte Fakten aus. Der Compiler selbst stellt dem Produktnutzer keine Fragen.

Das Beispiel prüft ausschließlich die modellierte Antragstellereignung unter den kuratierten Quellenrevisionen. Es beurteilt keine Heizungsmaßnahme, berechnet keinen Zuschuss und ist weder Beratung noch KfW-Zusage oder Förderentscheidung.

1. Übungsprodukt und Ausgaben erstellen

uv run --extra dev python tools/tutorial_workspace.py kfw
uv run --extra dev python tools/generate.py --product products/tutorial_kfw_458_eligibility
uv run --extra dev pytest -q products/tutorial_kfw_458_eligibility/tests

Erwartung: CLI- und HTTP-Nachweise bestehen. Decision-Spec, Quellenherkunft, autorisierten Fälle und HTTP-Spec werden getrennt verfasst, aber gemeinsam eingelesen.

2. Eine konkrete Anfrage senden

In PowerShell zunächst in das Übungsprodukt wechseln:

cd products/tutorial_kfw_458_eligibility
Get-Content -Raw -Encoding UTF8 ./examples/eligible-request.json |
  uv run --locked python app.py --contract ./generated/decision-contract.json
cd ../..

Erwartung für die mitgelieferte Anfrage: outcome: eligible und rule_set_version_label: 2026-07. Der Decision Request nennt die stabile Regelmenge und ein Datum, keine Wunschversion. Der Decision Result nennt die tatsächlich ausgewählte Version und die Herkunft.

3. Fehlende Fakten von falschen Fakten unterscheiden

Probiere eine Kopie der Anfrage mit weniger Fakten. Eine fehlende Eingabe wird als Fact Gap ausgewiesen. Solange das Ergebnis undeterminiert ist, kann die priorisierte Next Question zurückkommen. Der Client ergänzt die Antwort am genannten JSON Pointer und sendet den vollständigen Case erneut; es gibt keine serverseitige Sitzung.

Nachweisanforderungen werden separat bewertet. Ein passender Grundbuchbeleg erfüllt die erklärte Anforderung nur mit einer explizit akzeptierten Bewertung; das verändert nicht die Eigentumsbedingung oder den fachlichen Outcome. Semantik und Grenzen nachschlagen.

4. Die ausdrückliche HTTP-Abbildung lesen

specs/http_api.ttl beschreibt POST /eligibility-decisions, JSON-Schemas und Pointer für Anfrage, Resultat und Fehler. CLI und HTTP-Adapter nutzen dieselbe Decision-Auswertung, laufen aber als getrennte Prozesse. Ein gültiges negatives oder undeterminiertes Ergebnis ist kein HTTP-Fehler.

5. Einen deklarierten Status ändern

Ändere im Übungsprodukt in specs/http_api.ttl ausschließlich bei EligibilityHttpResult die Aussage sco:statusCode 200 auf sco:statusCode 202. Der Erfolg enthält weiterhin einen JSON-Body; 204/205 wären deshalb nicht unterstützt.

uv run --extra dev python tools/generate.py --product products/tutorial_kfw_458_eligibility
uv run --extra dev pytest -q products/tutorial_kfw_458_eligibility/tests

Erwartung: Generiertes OpenAPI und HTTP-Nachweise erwarten jetzt 202. Der datengetriebene Referenzadapter liest die regenerierte Abbildung, sodass seine HTTP-Antwort ebenfalls 202 verwendet. Die Decision-Fakten und Outcomes ändern sich nicht; die CLI-/HTTP-Paritätsnachweise bestehen weiterhin.

Starte manuell laufende Adapter nach der Regeneration neu. Wie du den Adapter manuell startest, steht im folgenden Abschnitt.

HTTP optional manuell ansehen

In einem PowerShell-Terminal im Übungsprodukt:

$env:HOST = '127.0.0.1'
$env:PORT = '8765'
uv run --locked python http_api.py --contract ./generated/decision-contract.json --openapi ./generated/expected-openapi.json

In einem zweiten Terminal desselben Verzeichnisses:

$body = Get-Content -Raw -Encoding UTF8 ./examples/eligible-request.json
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8765/eligibility-decisions' -ContentType 'application/json; charset=utf-8' -Body $body

/openapi.json zeigt die veröffentlichte Schnittstelle. Beende den manuellen Server mit Ctrl+C.
