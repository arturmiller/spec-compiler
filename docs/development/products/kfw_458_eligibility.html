KfW 458 applicant eligibility example

This versioned reference Product Bundle implements the bounded KfW 458 Applicant Eligibility Pilot. Its authored Turtle specs cite the December 2025 and July 2026 KfW Merkblatt revisions and define version-local Rules over six boolean Conditions with authored Fact Questions, two Evidence-applicability Conditions, one independently cited ownership Evidence Requirement, seven Conformance Cases, and the scoped outcomes eligible, ineligible, and unknown.

The implementation is a technology choice of this example. The CLI reads one JSON Decision Request from standard input and writes one JSON Decision Result to standard output through Decision Protocol v1. An additional HTTP adapter exposes the same request and result at POST /eligibility-decisions; its OpenAPI contract is generated from the explicit messages and body bindings in specs/http_api.ttl. The black-box tests also use the invoked Decision Contract for its authored cases and CLI parity. Generated tests invoke the manifest and never import product implementation modules. When Facts are missing and the outcome is still unknown, the result selects the lowest-priority current Fact Question and includes its Rule and Source Citation justification. A client adds the boolean answer at the returned JSON Pointer and submits the complete Case again; no session or UI is required by the protocol.

Each request names the stable Rule Set and an explicit Decision Date. Version Selection Conventions v1 select exactly one version from the authored half-open Validity Periods; callers cannot select a version and neither “today” nor “latest” is a default. The same usufruct-applicant facts are eligible on 2026-07-20 under revision 12/2025 and ineligible on 2026-07-21 under revision 07/2026. Every result reports the selected version and Decision Date.

For a self-using owner who claims the climate-speed or income bonus, the Decision Result evaluates the required land-register excerpt independently as fulfilled, missing, or not_applicable. Supplied Evidence is classified against the requirement and fulfills it only with a matching type and an explicit accepted Evidence Assessment. This Evidence evaluation never changes the ownership Condition or applicant-eligibility outcome. It requires no particular file format, upload protocol, storage system, or automatic document inspection.

The result covers only the modeled applicant-eligibility question. It does not assess heating measures, calculate a subsidy, provide legal or financial advice, or represent a KfW funding commitment or approval.

Run the example request manually

From this product directory in PowerShell, pipe the example JSON into the one-request CLI:

Get-Content -Raw -Encoding UTF8 .\examples\eligible-request.json |
  uv run --locked python app.py --contract .\generated\decision-contract.json

The result should report "outcome": "eligible" and "rule_set_version_label": "2026-07". Edit a copy of the request to try different facts or decision dates.

Run the HTTP API manually

From this product directory in one PowerShell terminal, start the HTTP adapter:

$env:HOST = '127.0.0.1'
$env:PORT = '8765'
uv run --locked python http_api.py --contract .\generated\decision-contract.json --openapi .\generated\expected-openapi.json

From the same directory in a second terminal, submit the same example request:

$body = Get-Content -Raw -Encoding UTF8 .\examples\eligible-request.json
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8765/eligibility-decisions' -ContentType 'application/json; charset=utf-8' -Body $body |
  Select-Object outcome, rule_set_version_label, next_question

GET http://127.0.0.1:8765/openapi.json returns the generated OpenAPI 3.1 document. Stop the server with Ctrl+C when finished. The HTTP API evaluates only the same bounded applicant-eligibility decision as the CLI.

Change the HTTP interface

Edit specs/http_api.ttl. It owns the endpoint path and three message resources:

  • EligibilityHttpRequest: JSON media type, required body, full JSON Schema, and the pointer selecting the Decision Request from the body.
  • EligibilityHttpResult: success status, JSON media type, full JSON Schema, and the pointer locating the complete Decision Result in the response.
  • EligibilityHttpError: invalid-request status, JSON media type, full JSON Schema, and the pointer locating the error text.

The schemas are authored JSON Schema literals inside Turtle. For example, changing the success message to sco:statusCode 202 changes the generated OpenAPI, adapter response, and test expectation. To return {"result": <Decision Result>}, set its sco:bodyPointer to "/result" and wrap the existing result schema in an object with a result property. Update both declarations together. Empty sco:bodyPointer "" means the whole body.

From the repository root, regenerate and verify:

uv run --extra dev poe run

Restart the HTTP adapter so it reloads the generated contract. The compiler copies these explicit schemas; it does not infer extra HTTP fields from the Decision Contract. Keep both contracts consistent when changing facts or outcomes. See HTTP Contract Conventions v1 for supported JSON Schema keywords and binding limits. The example HTTP adapter uses jsonschema as an implementation dependency.
