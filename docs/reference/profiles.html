Technische Referenz

Ein Ablauf, unterschiedliche Verträge.

Ein Verarbeitungsprofil bestimmt, welche expliziten Aussagen gelesen und welche Nachweise erzeugt werden. Es legt keine Produktimplementierungssprache fest.

SQL/OpenAPI-Profil

Das aktuelle Profil verlangt genau einen GET-Endpunkt, eine ausdrücklich deklarierte SQLite-Tabelle und eine gemeinsame Shape für Antwort und Speicherung. Skalare Properties mit sh:minCount 0 oder 1 und sh:maxCount 1 werden unterstützt. Strings, Dezimalzahlen und Integer besitzen Mappings; die Fixturesynthese deckt derzeit Strings und Dezimalzahlen ab.

Erzeugt werden erwartetes OpenAPI 3.1, direkte HTTP-/SQLite-Nachweise und Arbeitsaufträge. Offene Shapes erlauben zusätzliche Antwortfelder; nur sh:closed true verbietet sie. JSON wird direkt geprüft, nicht in RDF umgebaut. Mappingregeln · Ausführbares SQL-Tutorial.

Decision-Profil

Ein Decision Contract beschreibt eine begrenzte Entscheidungsfrage, explizite Regeln, mögliche Ergebnisse und ihre Herkunft. Ein Request nennt die stabile Regelmenge und ein ausdrückliches Datum. Genau eine Rule Set Version wird aus deklarierten halboffenen Gültigkeitszeiträumen ausgewählt; „heute“, „latest“ oder eine vom Aufrufer gewählte Version sind keine Defaults.

Boolesche Bedingungen werden als erfüllt, verletzt oder unbekannt bewertet. Ein Fact Gap ist fehlende Eingabe, nicht ein falsch gesetzter Fakt. Eine verletzte Bedingung kann das negative Ergebnis bereits bestimmen, obwohl andere Fakten fehlen. Nur ein undeterminiertes Ergebnis trägt die nach expliziter Priorität ausgewählte nächste Frage.

Obligations sind erklärte Pflichten; Evidence Requirements sind davon getrennte Nachweisanforderungen. Letztere benötigen anwendbare Bedingungen sowie passende, ausdrücklich akzeptierte Evidence. Beide Auswertungen verändern nicht die Regelauswertung oder den Decision Outcome.

Das Profil unterstützt keine automatische Quelleninterpretation, Disjunktionen, numerische Entscheidungsregeln, Sessions, Uploads, automatische Dokumentenprüfung oder allgemeine Pflichten-Lifecycle-Engine. Die vollständigen Decision-Konventionen und ihre Versions-, Frage- und Evidence-Erweiterungen sind normativ. Decision-Tutorial · Wiederverwendung und Pflichten.

Zusätzlich beschriebener HTTP-Vertrag

Das Decision-Produkt kann eine ausdrücklich spezifizierte POST-Schnittstelle besitzen. Pfad, Request-, Success- und Error-Schema, Status, JSON-Medientyp und Body-Pointer stammen aus der Produktspec. Der Vertrag wird zusätzlich zu OpenAPI und HTTP-Nachweisen übersetzt; gültige fachlich negative oder undeterminierte Ergebnisse verwenden die deklarierte Erfolgsantwort.

Der aktuelle Ausschnitt unterstützt einen festen POST-Pfad, erforderliche JSON-Bodies, einen Body erlaubenden 2xx-Status außer 204/205 und eine 4xx-Fehlerantwort. Schema-Referenzen, andere Methoden oder allgemeine Schemaäquivalenz werden nicht behauptet. HTTP Contract Conventions v1.

Profil für Compilerprodukte

Beim Profil für Compilerprodukte ist ein Compiler selbst das geprüfte Produkt, nicht ein neues Synonym für alle Verarbeitungsprofile. Eine Softwareanwendung deklariert Compiler Protocol v1 und einen Transformation Contract. Testeingaben nennen die geforderten Artefakte, das Fehlerverhalten bei fehlenden Specs und Ergebnisgleichheit. Optional beschreibt ein Bootstrap Process die Implementierungsherkunft; diese Herkunft ist nicht der Produktvertrag.
