Referenz · Processing Report Conventions v1

Welche Aussagen hat dieser Compilerlauf verwendet?

Das Unterstützungsinventar erklärt mögliche Fähigkeiten. Der Processing Report zeigt für ein konkretes Decision Product, welche verfassten Aussagen erfolgreich in eine benannte Interpretation und ein erzeugtes Artefakt eingegangen sind.

Bericht erzeugen und lesen

uv run python tools/generate.py --product products/kfw_458_eligibility

Die CLI erzeugt zusätzlich generated/processing-report.json und generated/processing-report.html im Product Bundle. Die HTML-Datei lässt sich lokal ohne Server öffnen und bietet Suche, Filter, Herkunftsdateien, Artefaktverweise und JSON Pointer. Sie lädt keine externen Skripte. Das bestehende Cloud Decision Product verwendet denselben Ablauf ohne HTTP.

Zuordnung und Aussagekraft

VerwendungBelegGrenze
VertragsverarbeitungEin erfolgreich normalisierter Wert oder eine ausdrücklich gebundene Ressourcenprojektion wird im gerenderten Artefakt wiedergefunden.Das ist eine Ableitungsbeziehung, kein eigener Verhaltenstest für jede Aussage.
StrukturprüfungEine ausgeführte Prüfung kontrolliert Modulgrenze, Singleton, expliziten Typ oder Vertragsbindung.Sie belegt keine fachliche Umsetzung im Produkt.
KontextübernahmeEine ausdrücklich übernommene beschreibende Information besitzt ein konkretes geprüftes Ziel, etwa den Titel einer Source Revision.Ein vorhandenes Label oder eine unbekannte Fachklasse wird nicht automatisch zu Kontext.
Semantisch nicht zugeordnetKeine erfolgreiche semantische Projektion ist aufgezeichnet.Das kann ungeklärte Information oder noch fehlende Instrumentierung sein. Es bedeutet weder Harmlosigkeit noch automatische Delegation.

Eine Aussage kann mehrere Verwendungen haben. semanticStatus unterscheidet contract, context und unassigned. processingStatus = structural-only ergänzt bei unassigned eine konkrete Readerprüfung über die gemeinsame Modulprüfung hinaus. Damit bleibt sichtbar, dass eine Bindung oder Typangabe geprüft wurde, ohne einen Verhaltenstest vorzutäuschen.

Konkrete Beispiele

  • Die explizite sco:invokesContract-Aussage eines POST-Endpunkts verweist auf den gelesenen Decision Contract. Der Bericht nennt sowohl die Bindungsprüfung als auch das konkrete Feld der generierten OpenAPI-Metadaten und den bestehenden HTTP-Arbeitsauftrag samt Nachweisreferenz.
  • Eine Condition mit factProperty und inputJsonPointer erscheint mit ihren normalisierten Feldern im Decision-Vertrag. Die verwendeten Fach-IRIs benötigen keine eigene Compilerfallunterscheidung.
  • Eine zusätzliche produktspezifische Ausnahmebeziehung an einem bekannten Decision Contract bleibt semantisch ungeklärt. Auch eine bekannte sco:path-Property auf einer unbeteiligten Ressource wird dadurch nicht zur API-Operation.
  • Ein ausdrücklich gelesener Source-Revision-Titel erscheint als Kontext mit seinem Zielfeld. Ein ungenutztes rdfs:label bleibt semantisch nicht zugeordnet.

Herkunft und reproduzierbare Identität

Jede Aussage enthält RDF-Termdaten, eine deterministische ID, relative Herkunftsdateien und getrennte uses. Importierte Definitionen werden nicht als Produktaussagen erfasst. Gleiche benannte Aussagen aus mehreren Dateien erhalten eine ID mit mehreren Herkunftsdateien.

Anonyme Knoten werden pro RDF-Datei kanonisiert. Ein Scope aus kanonischem Dateiinhalt und Vorkommensindex trennt identische anonyme Dateikopien. Bei gleichen geparsten RDF-Termdaten ändern Reihenfolge, Hash Seed, Arbeitsverzeichnis und reine Dateiumbenennung die semantische Aussageidentität im beschriebenen Scope nicht; Herkunftsdateien dürfen sich entsprechend ändern. Beliebige inhaltliche Änderungen oder neue Dateiscopes dürfen anonyme Identitäten ändern. Compilerquellhash, Bootstrap-Generation, Bibliotheksversionen, Konventionsreferenzen und Kataloghash machen die verwendete Werkzeugidentität sichtbar.

Geltungsbereich und offene Vertragsgrenze

Der Bericht gilt bislang für Decision und Decision mit explizitem HTTP-Vertrag. HTTP/SQL- und Compilerprofil weisen fehlende Berichtserfassung im CLI-Ergebnis aus; alte Berichtdateien werden nach erfolgreicher Verarbeitung entfernt. Der Bericht ändert keine Annahme-/Ablehnungslogik und keine fachlichen Produktpflichten. scope.contractCompleteness und scope.delegation lauten ausdrücklich not-assessed. Über die Bedeutung verhaltensrelevanter ungeklärter Aussagen entscheidet das Folgepaket #9.

Nachweisreferenzen stammen aus dem tatsächlich erzeugten Work Graph und benennen vorhandene generierte Tests. Der Bericht führt diese Tests nicht aus und beweist keine vollständige fachliche Prüfung. Ein neuer Readerpfad benötigt passende Aufzeichnung und überprüfte Projektionen. Fehler beim Berichtsrendering oder bei einer Projektionsprüfung lassen vorhandene Decision-Artefakte unverändert.
